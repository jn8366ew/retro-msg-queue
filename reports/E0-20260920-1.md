# E0-20260920-1 — 대조군: 아웃박스 없는 과거 방식

- 실행 시각: 2026-09-20 09:55 UTC (컨테이너 시각)
- BROKER_KIND: `redis` (정상 기동 상태 — 브로커 장애가 아니다)
- 플래그: `LEGACY_INLINE_PUBLISH=1`, `API_CRASH_AFTER_COMMIT=1`
- 단계: dev-plan §11 순서 3 / 결정 R12

## 목적

기획서 §1이 "실패 경계를 설명하는 비교 대상"으로만 두었던 경로를 실제로 실행한다. 면접 정리 8.7절의 한계 — *"큐에 전달되기 전에 누락된 작업은 PDF 실행 오류 알림 자체가 없을 수 있으므로, 알림만으로 모든 미발행을 발견한다고 보장할 수 없었다"* — 를 관측으로 재현하고 E3와 나란히 둔다.

`LEGACY_INLINE_PUBLISH=1`이면 API가 `outbox_events` 없이 `jobs`만 커밋하고 직접 `apply_async` 한다. `API_CRASH_AFTER_COMMIT=1`이 커밋과 발행 사이에 `os._exit(1)`을 넣는다.

## 실행한 명령 (순서대로)

```powershell
docker compose exec postgres psql -U app -d app `
  -c "TRUNCATE outbox_events, jobs RESTART IDENTITY CASCADE;"
```

docker compose --profile redis up -d --force-recreate api
docker compose exec api printenv LEGACY_INLINE_PUBLISH API_CRASH_AFTER_COMMIT

## 관측

**클라이언트가 받은 것**

```
NO RESPONSE: RemoteProtocolError: Server disconnected without sending a response.
exit=2
```

202도 500도 아니다. 연결이 그냥 끊겼다.

**컨테이너 상태** — `api:exited` (나머지 postgres·publisher·redis·worker는 running)

**DB에 남은 것**

```
 id |  request_key  | status  | event_id
----+---------------+---------+----------
  1 | E0-20260920-1 | PENDING |
```

`jobs` 행은 커밋됐다. `event_id`는 NULL — 아웃박스 행이 애초에 만들어지지 않았다.

**적체 관측**

```json
{"outbox_pending": 0, "oldest_pending_sec": 0.0, "sent_but_job_pending": 0,
 "attempts_ge_3": 0, "jobs_without_outbox": 1}
```

`outbox_pending`이 **0**이다. 발행자가 볼 대상이 없다.

**브로커** — `redis-cli llen jobs` → `0`

**워커 로그** — 이 `job_id`에 대한 라인 없음 (같은 시간대 라인은 E3·E4의 것)

**발행자 로그** — 이 `job_id`에 대한 활동 없음

**api가 남긴 로그**

```
09:55:33,438 INFO  app.api phase=legacy_committed job_id=1 ... request_key=E0-20260920-1
09:55:33,438 ERROR app.api phase=injected_crash   job_id=1 ... flag=API_CRASH_AFTER_COMMIT
```

**복구 후 대조 (모든 서비스 정상, 20초 이상 경과)**

```
 id |  request_key  |   job   | outbox | attempts
----+---------------+---------+--------+----------
  1 | E0-20260920-1 | PENDING |        |
  2 | E0-normal-1   | DONE    | SENT   |        1
```

`job_id=1`은 api를 복구하고 발행자·워커·브로커가 모두 정상인 상태로 20초 이상 지나도 **여전히 PENDING이다.** 아무도 이 건을 집어가지 않는다. 같은 조건에서 정상 경로로 들어온 `job_id=2`는 완료됐다.

## 결론

기대 관측과 일치한다. 커밋은 됐고 발행은 안 됐으며, **그 사실을 시스템 안에서 알 방법이 없다.**

E3와 나란히 놓으면 차이가 분명하다.

| | E0 (아웃박스 없음) | E3 (아웃박스) |
|---|---|---|
| 중단 후 DB | `jobs` 1행만 | `jobs` + `outbox_events(PENDING)` |
| 발행자가 볼 대상 | 없음 | PENDING 행 1건 |
| `backlog` 관측 | `outbox_pending: 0` | `outbox_pending: 1`, `oldest_pending_sec: 5.2` |
| 복구 | 안 됨. 영구 PENDING | 발행자 재시작 후 자동 발행 → DONE |
| 사람이 해야 할 일 | 누락 사실을 스스로 알아내고 수동 재실행 | 없음 |

아웃박스가 산 것은 "메시지가 안 사라진다"가 아니다. **"안 보냈다는 사실이 DB에 남는다"**이고, 그래서 발행자가 다음 주기에 그냥 집어간다.

### 주의 — 이 실험의 로그는 실제 상황보다 후한 조건이다

`phase=injected_crash` 라인은 `os._exit(1)` **직전에 일부러 남긴 것**이다. 실제 OOM이나 SIGKILL이라면 이 줄도 없다. 즉 현실은 여기서 본 것보다 나쁘다 — 면접 정리 6.3절이 짚은 *"OOM으로 프로세스 자체가 종료되는 경우에는 알림이 누락될 가능성"* 이 그것이다.

`phase=legacy_committed` 라인은 남지만, 그것만으로 "발행됐는지"는 알 수 없다. 뒤에 `legacy_published`가 없다는 **부재**를 근거로 삼아야 하는데, 로그 보존 기간·수집 실패·프로세스 강제 종료를 생각하면 신뢰할 근거가 못 된다. 면접 정리 3절의 *"실패 로그가 남은 작업만 찾는 것 ≠ 처리할 일을 먼저 기록하고 미완료를 찾는 것"* 이 이 차이다.

### `jobs_without_outbox: 1`이 탐지해 주지 않나

이 카운터가 누락을 잡아낸 것은 사실이다. 다만 **아웃박스 테이블이 있기 때문에** 비교 대상이 생긴 것이다. 진짜 레거시 시스템에는 그 테이블이 없으므로, 과거 보험 프로젝트가 실제로 했던 것처럼 *"가입 데이터의 증서 S3 경로가 없는 건을 확인"* 하는 식으로 업무 데이터끼리 대사해야 한다 (면접 정리 1절). 그것은 가능하지만 도메인마다 따로 만들어야 하고, 무엇보다 **자동 복구로 이어지지 않는다.** E0의 `job_id=1`은 탐지된 뒤에도 사람이 손대기 전까지 PENDING이다.

## 한계

- `outbox.SENT + jobs.PENDING` 상태는 "워커 미도달"과 "실행 중 중단"을 구분하지 못한다. 구분하려면 실행 시작 기록(점유 상태·시각)이 필요하다 (dev-plan §13-3). 이 실험은 그 상태에 도달하지 않지만 리포트 고정 항목으로 남긴다.
- 중단 지점은 `os._exit(1)`이다. 실제 OOM·SIGKILL·전원 차단은 재현하지 않았다. 다만 그 경우들은 이 실험보다 **불리한** 조건(로그도 없음)이므로 결론이 약해지지 않는다.
- E0은 아웃박스의 가치를 보이기 위한 대조군이며 정상 경로가 아니다. `LEGACY_INLINE_PUBLISH=1`은 실험 전용 플래그다.
- 이 실험은 DB 결과 저장만 다룬다. 외부 부작용(결제·파일·메일)의 누락·중복은 범위 밖이다.
