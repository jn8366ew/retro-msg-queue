## 묻는 것

발행자가 죽어 있는 동안 접수된 업무가 **유실되지 않고 적체로 남는가**, 그리고 발행자가 돌아오면 **스스로 복구되는가**. 브로커를 SQS로 바꿔도 이 성질이 유지되는지 확인한다.

## 관측

**접수 — 발행자가 죽어 있는 상태**

```
HTTP 202
{ "job_id": 1, "status": "PENDING" }
```

API는 발행자 상태와 무관하게 202를 반환한다. 접수는 DB 트랜잭션 하나로 끝나고 브로커를 건드리지 않기 때문이다.

**중단 중 상태 — `PENDING` / `PENDING`**

```json
{
  "job_id": 1,
  "status": "PENDING",
  "result": null,
  "created_at": "2026-09-21T00:55:29.334289Z",
  "completed_at": null,
  "outbox": {
    "event_id": 1,
    "status": "PENDING",
    "attempts": 0,
    "next_attempt_at": "2026-09-21T00:55:29.334289Z",
    "last_error": null,
    "published_at": null
  }
}
```

`attempts=0`이고 `last_error=null`이다. **발행을 시도했다가 실패한 것이 아니라 아직 아무도 집어가지 않은 상태**다. E4(브로커 접속 실패, `attempts≥2` + `last_error`)와 구분되는 지점이다.

**중단 중 적체**

```json
{"outbox_pending": 1, "oldest_pending_sec": 0.9, "sent_but_job_pending": 0, "attempts_ge_3": 0, "jobs_without_outbox": 0}
```

**중단 중 큐 상태**

```json
{ "ApproximateNumberOfMessages": "0", "ApproximateNumberOfMessagesNotVisible": "0" }
```

큐는 비어 있다. 업무는 DB의 아웃박스에만 있다 — 이것이 아웃박스 패턴의 요점이다. 브로커에 넣지 못했어도 기록은 남아 있다.

**발행자 재시작 후 전이**

```
[  0.03s] jobs=PENDING
[  0.03s] outbox=PENDING
[  0.45s] outbox=SENT
[  1.49s] jobs=DONE
```

**발행자 로그**

```

00:55:40,480 phase=published    job_id=1 event_id=1 task_id=fa6e36fb-7d15-411d-891b-59bcaaa0f0b5 attempt=1
00:55:40,486 phase=marked_sent  job_id=1 event_id=1 task_id=fa6e36fb-7d15-411d-891b-59bcaaa0f0b5 attempt=1
```

**워커 로그**

```
00:55:40,478 phase=start   job_id=1 event_id=1 execution_id=06908b38-... task_id=fa6e36fb-...
00:55:41,482 phase=adopted job_id=1 event_id=1 execution_id=06908b38-... task_id=fa6e36fb-...
```

**복구 후 적체**

```json
{"outbox_pending": 0, "oldest_pending_sec": 0.0, "sent_but_job_pending": 0, "attempts_ge_3": 0, "jobs_without_outbox": 0}
```

**식별자 연결** — `job_id=1` · `event_id=1` · `task_id=fa6e36fb-7d15-411d-891b-59bcaaa0f0b5` · `execution_id=06908b38-b4a6-481f-850d-fb460e0dad12`. `attempts=1`로 끝났다. 중단 중에는 시도 자체가 없었기 때문이다.

## 결론

기대 관측과 일치한다. 유실 없음, 자동 복구됨.

**발행자 기동에서 발행까지 0.284초다.** `PUBLISH_INTERVAL_SEC=1`보다 짧은 이유는 발행자 루프가 시작하자마자 첫 배치를 조회하기 때문이다 — 기다린 뒤 조회하는 것이 아니라 조회한 뒤 기다린다. 적체가 쌓여 있으면 재시작 즉시 소화된다는 뜻이고, Redis 실행([E3-20260920-1](E3-20260920-1.md))과 동일한 동작이다.

**브로커를 SQS로 바꿔도 이 실험의 결과는 달라지지 않는다.** 발행자가 죽은 동안에는 브로커와의 상호작용 자체가 없으므로, 브로커가 무엇인지는 관측에 영향을 주지 않는다. 이 실험이 확인하는 것은 브로커의 성질이 아니라 **DB 커밋과 발행을 분리한 구조의 성질**이다.

중단 중 상태가 `attempts=0` · `last_error=null`이라는 점이 중요하다. 적체의 원인이 "발행자 부재"인지 "브로커 장애"인지를 이 두 필드로 구분할 수 있다. 후자는 E4에서 `attempts≥2`와 `last_error`로 나타난다.

## 한계

- 발행자를 `docker compose stop`으로 정상 종료(SIGTERM)시켰다. 프로세스가 비정상 종료되어 발행 중이던 배치가 중간에 끊기는 경우는 이 실험이 다루지 않는다 — 그 경계는 E5(발행 후 기록 전 중단)에서 다룬다.
- 적체 1건만 확인했다. 배치 크기(`PUBLISH_BATCH_SIZE=10`)를 넘는 대량 적체의 소화 속도·순서는 측정하지 않았다.
- 발행자가 하나뿐인 전제다. 여러 발행자가 같은 아웃박스를 동시에 읽는 경우(`SKIP LOCKED` 필요)는 범위 밖이다 (dev-plan §13).
- `ApproximateNumberOfMessages`는 근사값이다. 중단 중 큐가 0이라는 관측은 `outbox_pending=1`과 함께 읽어야 의미가 있다.
- `outbox.SENT + jobs.PENDING` 상태는 "워커 미도달"과 "실행 중 중단"을 구분하지 못한다 (dev-plan §13-3).
- `task_acks_late=False`이므로 워커가 실행 중 죽으면 재전달되지 않는다. SQS visibility timeout과의 상호작용은 후속이다 (E8).
