## R9 실측 — 브로커 다운 시 `apply_async`

dev-plan §7 "2단계 검증 항목". `max_retries: 0`을 적용하기 **전에** 스펙 설정 그대로 측정했다.

| 조건 | 소요 | 예외 |
|---|---|---|
| redis 정상 (기준선) | 0.074초 | — (성공) |
| redis 없음, 스펙 설정 그대로 | 10.00 / 9.82초 | `kombu.exceptions.OperationalError` |
| `docker compose stop redis`, 스펙 설정 그대로 | 9.98 / 9.82초 | `kombu.exceptions.OperationalError` |
| `docker compose stop redis`, `max_retries: 0` 적용 | 4.03 / 3.85 / 3.85초 | `kombu.exceptions.OperationalError` |

오류 메시지는 네 경우 모두 동일했다.

```
Error -2 connecting to redis:6379. Name or service not known.
```

**해석**

- 예외 클래스는 소스 분석 예상대로 `kombu.exceptions.OperationalError`다. redis 드라이버 예외가 아니라 kombu가 감싼 것이므로 발행자의 `except`는 이것을 잡아야 한다.
- 소요 시간은 예상(≈6초)과 달랐다. **≈10초**다. 예상은 연결 거부가 즉시 실패한다고 가정했으나, 실제로는 `docker compose stop`이 컨테이너 DNS 항목을 지워 **이름 해석 실패**가 되고 그 자체가 ≈3.9초 걸린다. 타임라인: 시도(3.9초) → 대기 2초 → 시도(3.9초) → 누적 9.8초가 `broker_connection_timeout=4` 예산을 넘겨 raise.
- 컨테이너가 **없는 경우와 멈춘 경우의 결과가 같다.** 둘 다 DNS 해석 실패다. dev-plan §7이 예고한 그대로다.
- `max_retries: 0` 적용 후 **10초 → 3.9초**. 재시도 1회가 사라졌고, 남은 3.9초는 DNS 해석 자체의 시간이라 애플리케이션이 더 줄일 수 없다. 예상했던 100ms 미만은 연결 거부 상황에서만 나온다.

**E4에 대한 함의** — 실패 1회에 3.9초, `PUBLISH_RETRY_DELAY_SEC=3`이므로 `attempts=2`는 t≈5초에 도달한다. 적용 전이라면 t≈11초다. dev-plan §8의 E4 관측 창을 "5~15초"로 둔 근거가 이 수치다. 원래 v2의 "3~10초"는 적용 전 기준으로는 관측에 실패했을 것이다.

## 결론

기대 관측과 일치한다. `jobs.DONE`, `outbox.SENT`, `result.execution_id` 1개.

**`outbox.SENT`가 `jobs.DONE`보다 먼저 나타났다.** 발행자는 `apply_async` 반환 후 4밀리초 만에 SENT를 기록하는데(`published` 08:20:36,970 → `marked_sent` 08:20:36,974), 워커는 `TASK_DELAY_SEC=1`초를 쓴 뒤에야 DONE을 쓴다. dev-plan §4가 말한 "워커가 빠르면 DONE이 SENT보다 먼저 보일 수 있다"는 상태는 **E1에서 관측되지 않는다**. SENT를 아예 기록하지 않는 E5에서만 나타난다.

접수(08:20:35.919)에서 발행(08:20:36.970)까지의 약 1초는 발행자의 `PUBLISH_INTERVAL_SEC=1` 폴링 주기다. 커밋 직후 즉시 발행 경로가 없으므로 정상 흐름에서도 최대 1초의 발행 지연이 있다 (dev-plan §1 "후속" 항목).

## 한계

- `outbox.SENT + jobs.PENDING` 상태는 "워커 미도달"과 "실행 중 중단"을 구분하지 못한다. 구분하려면 실행 시작 기록(점유 상태·시각)이 필요하다 (dev-plan §13-3).
- 정상 흐름만 확인했다. 중단·중복·브로커 장애는 E3~E6b에서 다룬다.
- R9 실측의 3.9초는 이 환경의 DNS 해석 실패 시간이다. 브로커가 이름은 해석되지만 연결을 거부하는 상황(예: 프로세스만 죽은 경우)은 측정하지 않았으며, 그 경우 더 빠를 것으로 보이나 확인하지 않았다.
- `task_acks_late=False`이므로 워커가 태스크 실행 중 죽으면 브로커는 메시지를 재전달하지 않는다. 이 설정을 바꾸는 실험은 후속이다 (dev-plan §13-7, E8).
