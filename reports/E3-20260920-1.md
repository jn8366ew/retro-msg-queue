## 관측

**발행자 중단 중 접수** — `HTTP 202 {"job_id": 1, "status": "PENDING"}`

**중단 중 상태 (GET)**

```json

  "job_id": 1,
  "status": "PENDING",
  "result": null,
  "completed_at": null,
  "outbox": {
    "event_id": 1,
    "status": "PENDING",
    "attempts": 0,
    "next_attempt_at": "2026-09-20T09:53:49.918767Z",
    "last_error": null,
    "published_at": null

```

`attempts=0` — 발행자가 죽어 있으니 시도 자체가 없었다. `last_error`도 없다. 실패한 게 아니라 **아직 시작도 안 한** 상태다.

**적체 관측 (중단 중)**

```json
{"outbox_pending": 1, "oldest_pending_sec": 5.2, "sent_but_job_pending": 0,
 "attempts_ge_3": 0, "jobs_without_outbox": 0}
```

미발행 1건, 최장 대기 5.2초. **이 두 숫자가 과거 프로젝트에 없던 탐지 근거다.**

**브로커** — `redis-cli llen jobs` → `0` (아직 아무것도 안 보냈다)

**발행자 종료 로그**


`docker compose stop`의 SIGTERM을 핸들러가 받아 정상 종료했다. compose `command:`를 exec 배열로 쓴 덕분에 파이썬이 PID 1이다 (R7). `sh -c`로 감쌌다면 `sh`가 SIGTERM을 전달하지 않아 10초 뒤 SIGKILL 됐을 것이다.

**식별자 연결** — `job_id=1` · `event_id=1` · `task_id=2435cc80-8e2e-47de-aefa-e90458eadd6b` · `execution_id=4fe4091c-605f-41c9-a2c0-4f0f0cdf2eea`. 이벤트는 중단 전에 만들어진 것 그대로(`event_id=1`)이고, 메시지와 실행만 새로 생겼다.

## 결론

기대 관측과 일치한다. 발행자가 죽어 있어도 접수는 202로 성공하고, 발행 요청이 `outbox_events.PENDING` 행으로 남으며, 재시작하면 별도 조치 없이 이어서 발행한다.

**사람이 개입한 것은 `docker compose start publisher` 하나뿐이다.** 어떤 건이 밀렸는지 찾아내거나 수동으로 재실행할 필요가 없었다. 발행자는 로그가 아니라 DB의 PENDING 행을 조회하므로, 중단 중에 들어온 요청이든 중단 전에 들어온 요청이든 같은 방식으로 처리된다.

**E0과의 대조가 이 실험의 요점이다.** 같은 "커밋은 됐는데 발행 전에 중단" 상황에서:

| | E0 (아웃박스 없음) | E3 (아웃박스) |
|---|---|---|
| 중단 후 DB | `jobs` 1행만, `event_id` NULL | `jobs` + `outbox_events(PENDING, attempts=0)` |
| `backlog` | `outbox_pending: 0` | `outbox_pending: 1`, `oldest_pending_sec: 5.2` |
| 복구 절차 | 누락 사실을 스스로 알아내고 수동 재실행 | 프로세스 재시작만 |
| 결과 | 영구 PENDING | 1.3초 만에 DONE |

`attempts=0`이라는 값도 의미가 있다. 발행 실패(E4, `attempts≥1` + `last_error`)와 발행자 부재(E3, `attempts=0`)를 구별할 수 있다. 전자는 브로커·자격증명을 보고 후자는 프로세스를 본다.

## 한계

- `outbox.SENT + jobs.PENDING` 상태는 "워커 미도달"과 "실행 중 중단"을 구분하지 못한다. 구분하려면 실행 시작 기록(점유 상태·시각)이 필요하다 (dev-plan §13-3).
- 중단 방식은 `docker compose stop`(SIGTERM, 정상 종료)이다. `docker compose kill`(SIGKILL)로 이벤트 처리 도중 강제 종료하는 경우는 E5에서 다룬다.
- 복구는 사람이 `start`를 쳐서 이루어졌다. 프로세스 자동 재시작(`restart: always`)이나 적체가 임계치를 넘었을 때의 알림은 범위 밖이다 (dev-plan §2 제외 목록).
- `backlog`는 관측만 한다. 오래된 미발행 건을 자동으로 처리하지 않는다.
- 발행자가 하나뿐인 전제다. 여러 개를 띄우면 같은 이벤트를 동시에 집어갈 수 있고, `FOR UPDATE SKIP LOCKED` 같은 제어가 필요하다 (dev-plan §13-1).
