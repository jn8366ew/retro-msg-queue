## 결론

기대 관측과 일치한다. `jobs.DONE`, `outbox.SENT`, `result.execution_id` 1개, 큐 잔여 0.

**워커의 `phase=start`가 발행자의 `phase=published`보다 4밀리초 앞선다.** 로그만 보면 순서가 뒤집힌 것처럼 보이지만 모순이 아니다. `apply_async`가 SQS에 메시지를 넣고 반환하는 것과, 워커가 그 메시지를 받아 실행을 시작하는 것 사이에 발행자가 로그 한 줄을 쓸 뿐이다. 워커는 `wait_time_seconds=10` 롱 폴링으로 이미 대기 중이었기 때문에 메시지가 들어오자마자 깨어났다. **SQS 왕복이 발행자의 로그 한 줄보다 빨랐다**는 뜻이고, 이 환경에서 SQS 전달 지연이 밀리초 단위라는 실측이다.

이 순서 역전은 Redis 실행([E1-20260920-1](E1-20260920-1.md))에서는 나타나지 않았다. 거기서는 `published`(08:20:36,970)가 워커 `start`(08:20:36,969)와 1밀리초 차이로 사실상 동시였다. 브로커 종류가 아니라 로그 기록 순서와 스케줄링의 문제이며, 어느 쪽도 보장에 영향을 주지 않는다 — 보장은 조건부 UPDATE에 있다.

접수(00:54:12.385)에서 발행(00:54:13.554)까지의 1.17초는 발행자의 `PUBLISH_INTERVAL_SEC=1` 폴링 주기다. 커밋 직후 즉시 발행 경로가 없으므로 정상 흐름에서도 최대 1초의 발행 지연이 있다 (dev-plan §1 "후속" 항목). 이 값은 Redis 실행과 동일하며, 브로커 교체로 달라지지 않는다.

`outbox.SENT`가 `jobs.DONE`보다 먼저 기록됐다. Redis 실행과 같다.

## Redis 실행과의 차이

| 항목 | Redis (E1-20260920-1) | SQS (이 실험) |
|---|---|---|
| 접수→발행 | ≈1.05초 | ≈1.17초 |
| 발행→완료 | ≈1.01초 | ≈0.97초 |
| 브로커 잔여 | `llen jobs` → 0 | `ApproximateNumberOfMessages` → 0 |
| 관측 수단 | `redis-cli llen` | `aws sqs get-queue-attributes` |
| 자격 증명 | 없음 | `~/.aws` 마운트, IAM 사용자 |

정상 흐름에서는 두 브로커의 차이가 관측되지 않는다. 차이가 드러나는 지점은 장애·중복 실험이다.

## 한계

- `outbox.SENT + jobs.PENDING` 상태는 "워커 미도달"과 "실행 중 중단"을 구분하지 못한다. 구분하려면 실행 시작 기록(점유 상태·시각)이 필요하다 (dev-plan §13-3).
- 정상 흐름만 확인했다. SQS에서의 중단·적체는 E3, 중복은 E5에서 다룬다.
- `ApproximateNumberOfMessages`는 이름 그대로 **근사값**이다. Redis의 `llen`과 달리 즉시 정확한 값을 보장하지 않으므로, 0이라는 관측 하나로 "큐가 비었다"를 단정하지 않는다. 여기서는 `jobs.DONE`과 `execution_id` 단일성이 함께 관측됐기에 결론을 내렸다.
- SQS의 at-least-once 재전달은 이 실험에서 발생하지 않았다. 중복 전달을 강제로 만드는 실험은 E5·E6이며, visibility timeout 초과로 인한 재전달은 후속이다 (dev-plan §13-7, E8).
- `task_acks_late=False`이므로 워커가 태스크 실행 중 죽으면 브로커는 메시지를 재전달하지 않는다. SQS의 visibility timeout 30초는 이 설정 아래에서는 사실상 쓰이지 않는다 — 워커가 수신 직후 삭제하기 때문이다. 이 조합을 바꾸는 실험은 후속이다 (E8).
