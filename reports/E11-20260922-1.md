## 묻는 것

`reconcile`은 `stalled` 업무의 outbox 행을 조건부 UPDATE로 `PENDING`에 되돌려 발행자가 다시 보내게 한다. `gave_up`(미완료 실행 3건 이상)은 다시 보내지 않고 세기만 한다 (R22). 세 가지를 본다.

- ⓐ 멈춘 업무가 복구되는가
- ⓒ DLQ에 이미 격리된 업무를 되살리지 않는가
- ⓑ DLQ가 개입하지 않는 독약에서, `reconcile`이 만드는 반복이 3회에서 멈추는가

실행 순서는 ⓐ → (E10④) → ⓒ → ⓑ다.

`reconcile`의 출력 원문은 전달받지 못했다. 실행 직후 DB는 job 3의 outbox가 `SENT`, `attempts=1`, `last_error` 없음, 실행 기록 3행 그대로였다. `reconcile`이 재발행했다면 `attempts=2`와 `reconciled: stalled`가 남았어야 한다. 재발행하지 않았다.

## ⓑ DLQ 없는 독약에서 상한

`acks_late=False`면 워커는 받자마자 ACK하므로, 자식이 죽어도 브로커는 다시 보내지 않고 DLQ도 개입하지 않는다. 반복을 만드는 것은 `reconcile`뿐이다.

```powershell
docker compose exec postgres psql -U app -d app `
  -c "TRUNCATE outbox_events, jobs RESTART IDENTITY CASCADE;"
Remove-Item Env:\TASK_ACKS_LATE; Remove-Item Env:\TASK_REJECT_ON_WORKER_LOST
docker compose up -d --force-recreate worker
docker compose exec api python experiments/run.py create --request-key E11-b --value 7
# 아래 세 줄 반복
Start-Sleep -Seconds 65
docker compose exec api python experiments/run.py backlog --detail
docker compose exec api python experiments/run.py reconcile
```

`TASK_CRASH_BEFORE_ADOPT=1`, `TASK_DELAY_SEC=1`은 E10④에서 남아 있었다.

## 결론

기대 관측과 일치한다. **`reconcile`은 멈춘 업무를 새 메시지로 되살렸고(ⓐ), 이미 격리된 업무는 건드리지 않았으며(ⓒ), 자기가 만든 반복을 3회에서 멈췄다(ⓑ).**

**같은 "3회 후 멈춤"을 서로 다른 장치가 만들었다.**

| | E10④ (E9 재현) | E11ⓑ |
|---|---|---|
| 다시 보낸 주체 | SQS 브로커 (미ACK 메시지 재전달) | `reconcile` (outbox → PENDING → 발행자) |
| `task_id` | 세 번 모두 같음 (`b1283274`) | 세 번 모두 다름 |
| 간격 | 11.2초, 9.5초 (`wait_time_seconds`) | 82.0초, 137.7초 (사람이 `reconcile`을 돌린 시점) |
| 멈춘 장치 | DLQ maxReceiveCount 3 | `RECONCILE_MAX_UNFINISHED` 3 |
| 남은 흔적 | DLQ 메시지 1개, outbox attempts 1 | outbox attempts 3, `last_error` |

두 상한이 같은 3이어서 ⓒ가 성립한다. DLQ가 3회에서 끊은 업무는 DB에서도 미완료 3건이므로 `gave_up`이 되고, `reconcile`은 그것을 다시 시작하지 않는다. 상한이 없었다면 `reconcile`은 DLQ가 끊은 반복을 DB 쪽에서 다시 시작했을 것이다 (R22).

**60초 기준은 성급한 재발송도 막았다.** ⓑ 2회차에서 50초 만에 `reconcile`을 돌렸지만 업무는 `running`으로 분류돼 재발행되지 않았다. 실제로는 죽은 실행이었지만, DB는 60초 전까지 그것을 계산 중과 구분하지 않고 기다린다. 기준이 없었다면 실행 중인 업무를 중복 발행했을 것이다(중복 결과는 조건부 UPDATE가 막지만 실행은 두 번 일어난다).

**`last_error`는 성공 뒤에도 남는다.** ⓐ의 job 1은 `DONE`인데 outbox에 `reconciled: stalled`가 있다. 오류가 아니라 복구 이력이다.

**멈춘 뒤에는 사람이 나서야 한다.** ⓑ의 job 1은 `gave_up`으로 `PENDING`에 남았다. 원인(독약)을 고친 뒤 `run.py republish`로 직접 다시 보내야 끝난다. E10④의 job 3은 DLQ redrive가 필요하다. 이번 실습에서는 둘 다 하지 않았다.

## 한계

- **ⓐ에서 재발송 메시지가 실행되기까지 30.1초가 걸렸고, 원인을 확인하지 못했다.** 발행 10:50:50.56 → 시작 10:51:20.65. 큐 VisibilityTimeout 30초와 거의 같다. 워커를 다시 만든 지(10:50:45) 5초 만에 도착한 메시지였다. 그런데 ⓑ에서는 같은 경로가 1.6~1.8초였다. 워커가 기동하는 도중에 메시지를 한 번 받고 처리하지 못해, 30초 뒤 다시 보이게 됐을 가능성이 있다. 하지만 그 워커의 로그는 다음 `--force-recreate`(10:51:25) 때 컨테이너와 함께 지워졌다. 메시지도 이미 삭제돼 `ApproximateReceiveCount`를 볼 수 없다. 재현하려면 워커 재생성 직후 `reconcile`을 돌리고, 다음 재생성 전에 로그와 수신 횟수를 먼저 확보해야 한다.
- ⓒ의 `reconcile` 출력 원문이 없다. 결과는 DB 상태로 판정했다.
- ⓑ의 반복 간격은 사람이 명령을 친 시점이다. 자동 복구(발행자 루프 안의 주기 복구)는 범위 밖이다 (R22).
- `gave_up` 업무를 사람이 복구하는 절차(`republish`, DLQ redrive)와, 복구 뒤 완료되는지는 확인하지 않았다.
- `reconcile`의 재발행과 워커의 늦은 완료가 경합하는 경우(예: 60초를 넘긴 정상 작업)는 만들지 않았다. 설계상 재발행된 메시지는 `already_done`으로 끝나야 한다 (R22, E5·E6b).
- `reconcile`은 `stalled`만 다룬다. 워커에 닿기 전에 사라진 메시지(`not_started`에 머무는 업무)는 구하지 못한다 — [E10](E10-20260922-1.md) 한계 참조.
