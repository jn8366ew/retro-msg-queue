# E2-20260920-1 — 트랜잭션 롤백 (jobs 저장 후 outbox 저장 전 예외)

- 실행 시각: 2026-09-20 05:48~05:49 UTC (컨테이너 시각)
- BROKER_KIND: 해당 없음 — 1단계에는 브로커 코드 경로가 없다 (api·postgres만 기동)
- 이미지·패키지 버전: README "패키지·이미지 버전" 표 참조
- 단계: dev-plan §11 순서 1

## 관측

**사전 상태** (E7 실행 후) — `jobs=1, outbox_events=1, jobs_id_seq.last_value=3`

**플래그 확인** — 컨테이너 안 `API_CRASH_BEFORE_OUTBOX=1`

**create 응답**

```
HTTP 500
Internal Server Error
```

**api 로그**

```
2026-09-20 05:48:49,730 ERROR app.api phase=injected_crash job_id=4 event_id=- execution_id=- task_id=- attempt=- flag=API_CRASH_BEFORE_OUTBOX
  File "/app/app/main.py", line 98, in create_job
    raise RuntimeError("injected: API_CRASH_BEFORE_OUTBOX=1")  # → 500, 전체 롤백
RuntimeError: injected: API_CRASH_BEFORE_OUTBOX=1
```

`job_id=4`는 `flush()`가 시퀀스에서 받아 온 값이다. 커밋되지 않았다.

**해당 request_key 행 수 (run.py count)**

```
{"request_key": "E2-20260920-1", "jobs": 0, "outbox_events": 0}
```

**전체 행 수 + 시퀀스 (psql)**

```
1|1|4
```

`jobs`·`outbox_events` 전체 행 수는 사전 상태(1/1)와 같다. 시퀀스만 3 → 4로 올랐다.

**브로커** — 1단계에는 브로커 서비스도, 브로커에 연결하는 코드 경로도 없다. 아래 "결론" 참조.

**플래그 해제 후 같은 request_key 재접수**

```
HTTP 202
{ "job_id": 5, "status": "PENDING" }
{"request_key": "E2-20260920-1", "jobs": 1, "outbox_events": 1}
```

`job_id=5`로 새로 접수됐다 — 롤백된 `job_id=4` 행이 `request_key`를 점유하고 있지 않았다는 증거다. UNIQUE 충돌(409/200)이 아니라 202가 나왔다.

## 결론

기대 관측과 일치한다. `jobs` INSERT 후 `outbox_events` INSERT 전에 예외가 나면 두 테이블 모두 롤백되고 500을 반환한다. 해당 `request_key`의 행은 어느 테이블에도 남지 않는다.

**"브로커에 메시지 없음"은 관측이 아니라 구조적 보장이다.** API는 브로커에 연결하지 않으며(dev-plan §5), 1단계에는 브로커 서비스 자체가 없다. 따라서 이 항목은 "확인했다"가 아니라 "그런 코드 경로가 존재하지 않는다"로 기록한다. 2단계에서 redis를 띄운 뒤 `docker compose exec redis redis-cli llen jobs`를 접수 전후로 비교해 경험적으로 재확인한다.

`jobs_id_seq`가 3 → 4로 오른 것은 정상이다. PostgreSQL의 시퀀스는 롤백되지 않으므로 이후 `job_id`가 불연속이 된다. 행이 유실된 것이 아니다.

## 한계

- `outbox.SENT + jobs.PENDING` 상태는 "워커 미도달"과 "실행 중 중단"을 구분하지 못한다. 구분하려면 실행 시작 기록(점유 상태·시각)이 필요하다 (dev-plan §13-3).
- 이 실험이 보여주는 것은 **한 DB 안의 두 테이블**이 원자적으로 저장·롤백된다는 것뿐이다. DB와 브로커를 하나의 원자적 트랜잭션으로 묶은 것이 아니다 (dev-plan §10).
- 중단 지점은 애플리케이션 코드의 `raise`다. 프로세스 강제 종료(SIGKILL)나 DB 연결 단절 같은 다른 중단 방식은 확인하지 않았다.
- 브로커 항목은 위 결론대로 구조적 보장이며 경험적 관측이 아니다.
