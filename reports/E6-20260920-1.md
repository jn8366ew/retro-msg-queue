## 관측

**정상 완료 (재발행 전)**

```
[  0.03s] jobs=PENDING
[  0.03s] outbox=SENT
[  1.07s] jobs=DONE
```

**재발행 2회**

```json
{"event_id": 1, "job_id": 1, "task_id": "448d6da5-1a90-4fca-b4a5-2abafee85da6"}
{"event_id": 1, "job_id": 1, "task_id": "1c17f21d-8d84-4de9-bca1-ef8d15ac4fb2"}
```

같은 `event_id`·같은 `job_id`, `task_id`만 새로 생겼다.

**워커 로그**

```

11:43:33,737 phase=start        execution_id=66ac8ff0-... task_id=1c17f21d-...   ← 재발행 2
```

세 번 실행됐고 `adopted`는 첫 번째뿐이다. 재발행된 두 건은 `start`에서 `already_done`까지 **1~2밀리초**다 — `TASK_DELAY_SEC=1`을 쓰지 않았다.

**최종 GET**

```json
{
  "status": "DONE",
  "result": {
    "value": 7, "square": 49,
    "execution_id": "5717c8bb-ce1a-47ef-9c13-aff67ed5c2d8"
  },
  "completed_at": "2026-09-20T11:43:28.687705Z",
  "outbox": {
    "event_id": 1, "status": "SENT", "attempts": 1,
    "published_at": "2026-09-20T11:43:27.684552Z"
  }

```

`result.execution_id`는 첫 실행 값(`5717c8bb`), `completed_at`도 불변이다.

**`attempts`가 1 그대로다.** `republish`는 `send_compute`만 호출하고 `outbox_events`를 건드리지 않는다 (dev-plan §0 v2 #7). 그래서 브로커에 3번 들어갔지만 아웃박스 기록상 시도는 1회다.

## 결론

기대 관측과 일치한다. 같은 이벤트가 세 번 전달돼도 채택된 DB 결과는 하나이고 바뀌지 않았다.

### `already_done`이지 `rejected_already_done`이 아니다

세 실행이 시간상 겹치지 않았기 때문이다. concurrency=1 · prefork · `prefetch_multiplier=1`이라 메시지는 **엄격히 직렬**로 처리된다. 두 번째 실행이 시작할 때 첫 번째는 이미 커밋을 끝냈고, 그래서 사전 조회(`if job.status == "DONE"`)에서 곧바로 반환했다.

즉 **이 실험에서 중복을 걸러낸 것은 사전 조회이고, 조건부 UPDATE는 실행조차 되지 않았다.** 사전 조회는 계산을 건너뛰는 최적화일 뿐 보장 장치가 아니므로(면접 정리 3절 *"사전 조회만으로 동시 실행을 막을 수 없다"*), 이 결과만으로 멱등성이 확인됐다고 말할 수 없다. 조건부 UPDATE의 `rowcount=0` 분기는 E6b에서 확인한다.

### `republish`가 무엇과 다른가

면접 정리 7.5절이 구분한 세 가지 중 **수동 재실행**에 해당한다.

| 구분 | 누가 다시 실행시키는가 | 이 MVP에서 |
|---|---|---|
| Celery retry | 코드·설정이 오류를 재시도 대상으로 판단 | 없음 (`autoretry_for` 미설정) |
| 브로커 재전달 | visibility timeout 만료 등 | 없음 (`acks_late=False`) — E8 후속 |
| 수동 재실행 | 운영자가 상태 확인 후 요청 | **`run.py republish`** |

발행자가 쓰는 것과 **같은 `send_compute` 함수**를 호출한다. 별도 경로를 만들지 않았으므로, 여기서 관측한 중복 내성은 발행자가 재발행할 때(E5)와 같은 조건이다.

## 한계

- `outbox.SENT + jobs.PENDING` 상태는 "워커 미도달"과 "실행 중 중단"을 구분하지 못한다. 구분하려면 실행 시작 기록(점유 상태·시각)이 필요하다 (dev-plan §13-3).
- **조건부 UPDATE를 검증하지 않았다.** 직렬 실행이라 `rowcount=0` 경로에 도달하지 않는다. E6b 참조.
- 재발행 사이 간격이 3~4초였다. `TASK_DELAY_SEC=1`보다 크므로 겹칠 수 없었다.
- 계산 자체는 반복되지 않았다(사전 조회가 막았다). 하지만 그것은 우연히 타이밍이 어긋난 결과이지 보장이 아니다 — E6b에서는 두 실행이 모두 계산을 수행한다.
- DB 결과 저장만 다룬다. 외부 부작용의 중복은 범위 밖이다.
