# E6b-20260920-1 — 중복 전달 (동시) · 조건부 UPDATE 실증

- 실행 시각: 2026-09-20 11:44 UTC (컨테이너 시각)
- BROKER_KIND: `redis` (정상)
- 설정: worker `--concurrency=2 --pool=prefork`, `TASK_DELAY_SEC=3`, 발행자 중지
- 단계: dev-plan §11 순서 4 / 결정 R13
- **§1 제약(concurrency=1)의 의도적 이탈.** 이 실험에서만 2로 올린다

## 왜 이 실험이 필요한가

E5·E6에서 중복 전달을 재현했지만 둘 다 `already_done`으로 끝났다. concurrency=1에서는 메시지가 엄격히 직렬 처리되므로, 두 번째 실행이 시작할 때 첫 번째는 이미 커밋을 마쳤고 **사전 조회**(`if job.status == "DONE"`)가 먼저 걸린다.

그 결과 이 MVP의 핵심 장치인 조건부 UPDATE — `UPDATE jobs ... WHERE id=? AND status='PENDING'`의 `rowcount=0` 분기 — 는 E1~E7 어느 실험에서도 실행되지 않는다. 검증되지 않은 보장을 문서에 적을 수 없으므로 동시 실행 조건을 만든다.

읽어야 할 것이 네 가지다.

## 결론

기대 관측과 일치한다. **조건부 UPDATE의 `rowcount=0` 분기가 실제로 실행됐고, 나중 실행이 먼저 채택된 결과를 덮어쓰지 못했다.**

### 사전 조회는 보장이 아니다 — 이 실험이 증명한 것

| | E6 (직렬) | E6b (동시) |
|---|---|---|
| 두 번째 실행의 사전 조회 | `DONE` 발견 → 즉시 반환 | `PENDING` 발견 → **통과** |
| 계산 수행 | 안 함 (1~2ms) | 함 (3.03초) |
| 걸러낸 주체 | 사전 조회 | **조건부 UPDATE** |
| 로그 | `already_done` | `rejected_already_done` |

E6만 보면 "사전 조회가 중복을 막는다"고 오해할 수 있다. E6b는 그 조회가 **아무것도 막지 못하는 경우**를 보여준다. 두 실행이 겹치면 둘 다 `PENDING`을 읽고 둘 다 계산한다. 유일한 방어선은 `WHERE status='PENDING'` 조건이 붙은 UPDATE이고, PostgreSQL Read Committed에서 경합 시 조건이 재평가되므로 한쪽만 1행을 갱신한다.

면접 정리 3절의 *"두 워커가 사전 조회에서 모두 '없음'을 확인할 수 있다. 최종 중복 생성은 DB 제약이 방어한다"*, Q6의 조건부 UPDATE `rowcount` 1/0 판정이 이것이다.

### 보장하는 것과 보장하지 않는 것

이 실험이 보여주는 것은 **"실행이 한 번뿐"이 아니라 "채택이 한 번뿐"** 이다. 계산은 확실히 두 번 실행됐다(3초씩, 두 프로세스에서). 보장은 *같은 업무의 완료 결과가 한 번 채택되고 덮어써지지 않는다*까지다.

면접 정리 9.4~9.5절이 S3 파일로 다룬 구조 — 실행별 경로에 저장하고 현재 토큰으로 DB 갱신에 성공한 결과만 채택 — 를 파일 없이 DB만으로 축소한 형태다. `execution_id`가 "실행별 경로"에 해당하고, 조건부 UPDATE가 "채택 포인터"에 해당한다. 다만 이 MVP는 DB 밖에 아무것도 쓰지 않으므로, 거절된 실행이 남긴 쓰레기를 정리할 필요가 없다. 실제 파일·외부 호출이 있다면 그 정리와 중복 방지는 별도 설계가 필요하다.

### 설정 이탈 기록 (R13)

dev-plan §1 제약은 "워커 1개(concurrency=1)"이고 §12는 그 값을 바꾸지 말라고 한다. 이 실험에서만 2로 올렸다. 이유는 위 "왜 이 실험이 필요한가"이며, 다른 실험(E1~E6)은 모두 concurrency=1로 수행했다. 실험 종료 후 1로 되돌렸다.

`TASK_DELAY_SEC`도 1 → 3으로 올렸다. 두 실행이 겹칠 창을 넓히기 위해서다. 1초로는 컨테이너 exec 오버헤드 때문에 두 번째 메시지가 창 밖에 떨어질 수 있다.

## 한계

- `outbox.SENT + jobs.PENDING` 상태는 "워커 미도달"과 "실행 중 중단"을 구분하지 못한다. 구분하려면 실행 시작 기록(점유 상태·시각)이 필요하다 (dev-plan §13-3).
- 동시성을 인위적으로 만들었다. 두 메시지를 병렬 호출로 던지고 `TASK_DELAY_SEC`을 3배로 늘렸다. 실제 운영에서 이 경합이 얼마나 자주 일어나는지는 이 실험이 말해주지 않는다.
- 두 실행의 간격이 1밀리초다. 더 벌어진 경우(예: 재선점 만료 후 늦은 워커가 뒤늦게 완료를 시도하는 상황)는 확인하지 않았다. 그 경우 토큰·버전이 필요하다 (면접 정리 9.3, dev-plan §13-3).
- **계산은 두 번 실행됐다.** 외부 부작용이 있는 태스크라면 이 구조로 그 중복을 막지 못한다 (dev-plan §2, §10).
- 채택 판정은 `status='PENDING'` 하나에만 의존한다. 재발행 버전(같은 업무의 새 버전)을 구분하려면 `version` 조건이 추가로 필요하다 (dev-plan §13-8).
- `acks_late=False`이므로 워커가 실행 중 죽으면 브로커는 재전달하지 않는다 (dev-plan §13-7, E8).
