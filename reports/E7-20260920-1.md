# E7-20260920-1 — HTTP 중복 접수

- 실행 시각: 2026-09-20 05:48 UTC (컨테이너 시각)
- BROKER_KIND: 해당 없음 — 1단계에는 브로커 코드 경로가 없다 (api·postgres만 기동)
- 이미지·패키지 버전: README "패키지·이미지 버전" 표 참조
- 단계: dev-plan §11 순서 1

docker compose up -d --build

## 관측

**1) 최초 접수 — 202**

```
HTTP 202
{ "job_id": 1, "status": "PENDING" }
```

**2) 같은 request_key · 같은 value — 200, GET과 같은 본문**

```
HTTP 200
{
  "job_id": 1,
  "status": "PENDING",
  "input": { "value": 7 },
  "result": null,
  "created_at": "2026-09-20T05:48:29.029163Z",
  "completed_at": null,
  "outbox": {
    "event_id": 1, "status": "PENDING", "attempts": 0,
    "next_attempt_at": "2026-09-20T05:48:29.029163Z",
    "last_error": null, "published_at": null
  }
}
```

`job_id`가 1로 동일하다. 새 행을 만들지 않고 기존 행을 반환했다.

**3) 같은 request_key · 다른 value — 409**

```
HTTP 409
{ "detail": "request_key already used with different input" }
```

**4) 행 수 (run.py count)**

```
{"request_key": "E7-20260920-1", "jobs": 1, "outbox_events": 1}
```

**5) 행 수 (psql 직접 조회)**

```
1|1
```

**관련 로그 라인**

```
phase=accepted         job_id=1 event_id=1 ... request_key=E7-20260920-1
phase=duplicate_same   job_id=1 event_id=- ... request_key=E7-20260920-1
phase=duplicate_conflict job_id=1 event_id=- ... request_key=E7-20260920-1
```

## 결론

기대 관측과 일치한다. 같은 입력의 재요청은 같은 `job_id`로 200, 다른 입력은 409, 세 번의 요청 동안 `jobs`·`outbox_events` 행 수는 각각 1로 불변이다.

사전 SELECT로 중복을 거르지 않고 `request_key` UNIQUE 제약의 `IntegrityError`를 잡아 사후 처리했다. 면접 정리 8.8절의 "DB 중복 INSERT가 거절된 것과 API가 기존 성공 결과를 반환한 것은 다르다 — 후자의 실제 처리는 미확인"에 대응하는 확인이다.

## 한계

- `outbox.SENT + jobs.PENDING` 상태는 "워커 미도달"과 "실행 중 중단"을 구분하지 못한다. 구분하려면 실행 시작 기록(점유 상태·시각)이 필요하다 (dev-plan §13-3).
- 이 실험은 동시 요청이 아니라 순차 요청이다. 두 요청이 같은 순간에 들어오는 경합은 확인하지 않았다. UNIQUE 제약이 최종 방어선이라는 구조는 같지만, 관측한 것은 직렬 재요청이다.
- 1단계에는 발행자·워커가 없으므로 접수 이후 상태 전이는 확인 범위 밖이다.
